# V_q kernel fix plan (Round 9 / orchestrator-implemented)

## Goal

Eliminate the 30 `Involuntary full rematerialization` warnings at `v_q_g_flat.py:95` and the apparent compile-time bloat that turned ~50 s of kernel work into ~3 h of wall time at CrI3 6×6 80 Ry. Recipe parallels the wfn/pair-density fix in Round 6+7: stage sharding transitions cleanly, convert Python-unrolled outer loop to `lax.scan`, audit/reduce `with_sharding_constraint` density.

## What's wrong, precisely

`sources/lorrax_B/src/gw/v_q_g_flat.py`:

### Issue 0 — IBZ-vs-full-BZ fallback (line 154-204) ← biggest savings at scale

The code tries IBZ-only iteration via `_resolve_ibz_q_list()` → `compute_centroid_sym_perm()`. When centroids don't have orbit closure under the symmetry group, `compute_centroid_sym_perm()` raises `RuntimeError`, `sym_perm = None`, `use_ibz = False`, and the code **silently falls back to full-BZ iteration** — 36 q-points at CrI3 6×6 instead of the ~6-9 IBZ q-points. ~4-6× compute multiplier on every V_q + Σ_X stage.

The CrI3 80 Ry run hit this: log says "Total failures: 7444 / 9024." Centroids generated by plain kmeans aren't orbit-closed; the unfold table can't be built.

**Fix paths** (one of these, possibly both):

- **0a) Orbit-aware kmeans** — regenerate centroids with kmeans constrained to produce a symmetry-closed set. After regeneration, the existing IBZ path works without code changes in v_q_g_flat.py. The error message even points at this: "Regenerate centroids with orbit-aware kmeans or fall back to identity-only sym." Code site: `centroid/kmeans_isdf.py` (probably) and `centroid/orbit_syms.compute_centroid_sym_perm`.

- **0b) Decouple IBZ iteration from sym_perm availability** — always iterate IBZ q-list (the `find_irreducible_qpoints()` call doesn't require centroid orbit closure; it's purely about the k-grid + space group). When sym_perm fails, either:
  - Map each `S@μ` to the nearest centroid via a `KDTree` lookup (approximate unfold, introduces a per-non-closed-centroid error of ~grid-spacing class).
  - Or REFUSE with a hard error pointing the user to regenerate centroids. Don't silently fall back to 6× more compute.

**Priority**: Issue 0 is independently worth doing and probably faster wall-time payoff than Issues 1-3 combined. Recommend doing 0b (refuse path) plus a follow-up to 0a (orbit-aware kmeans).

### Issue 1 — combined slice + reshard (line 93-94)

```python
zeta_L_3d = jax.lax.with_sharding_constraint(zeta_L_q, blk_xy_sh)   # P(('x','y'), None)
# ...
zeta_L = jax.lax.with_sharding_constraint(zeta_L_3d[0], blk_x_sh)    # P('x', None)
```

`zeta_L_3d[0]` simultaneously (a) reduces rank 3 → 2 by dropping the leading q axis, and (b) the WSC reshards from flat-`('x','y')` to `'x'`-only. XLA SPMD partitioner cannot plan that as a single mesh-aware op, falls back to full rematerialization of `c128[1, 1504, 59990]` = 14.4 GB. This fires 15 times per side × 2 sides = 30 warnings per compile.

**Fix**: split into two cleanly-plannable ops. Two equivalent options, pick whichever XLA actually plans better (test both):

- **Option A** (reshard first, then slice — leaves slicing as pure local op):
  ```python
  zeta_L_3d_resharded = jax.lax.with_sharding_constraint(
      zeta_L_3d, NamedSharding(mesh_xy, P(None, 'x', None)))
  zeta_L = zeta_L_3d_resharded[0]  # local index, no reshard
  ```
- **Option B** (slice first, then reshard — leaves slice at existing sharding):
  ```python
  zeta_L_2d = zeta_L_3d[0]  # rank-3 → rank-2 at existing P(('x','y'), None) sharding
  zeta_L = jax.lax.with_sharding_constraint(zeta_L_2d, blk_x_sh)
  ```
  Slicing axis 0 of a `P(('x','y'), None)` sharded tensor is a local op (axis 0 is replicated within the flat sharding); reshape rank doesn't change which axes are sharded.

Same fix applies to `zeta_R_3d[0]`.

### Issue 2 — Python-unrolled outer q-loop (line 431)

```python
for q in range(n_q_ibz):
    zeta_L_q = jax.lax.dynamic_slice_in_dim(zeta_L_all, q, 1, axis=0)
    zeta_R_q = (zeta_L_q if same_zeta
                else jax.lax.dynamic_slice_in_dim(zeta_R_all, q, 1, axis=0))
    V_acc, g0_acc = kernel(V_acc, g0_acc, zeta_L_q, zeta_R_q, v_q_dev[q], jnp.int32(q))
    jax.block_until_ready(V_acc)
```

`zeta_L_all` and `zeta_R_all` are already device-resident, so no I/O. But the loop:
1. Forces a `block_until_ready` synchronization per q (no async overlap).
2. Dispatches the jitted kernel 36 separate times — each Python step has overhead.
3. Dispatches the kernel 36 separate times — XLA may not be able to fuse cross-q optimizations.

**Fix**: convert to `lax.scan` over q with `(V_acc, g0_acc)` as carry. Pattern (pseudocode):

```python
def _per_q_body(carry, q_idx):
    V_acc, g0_acc = carry
    zeta_L_q = jax.lax.dynamic_slice_in_dim(zeta_L_all, q_idx, 1, axis=0)
    zeta_R_q = (zeta_L_q if same_zeta
                else jax.lax.dynamic_slice_in_dim(zeta_R_all, q_idx, 1, axis=0))
    V_acc, g0_acc = kernel_body(V_acc, g0_acc, zeta_L_q, zeta_R_q,
                                v_q_dev[q_idx], q_idx)
    return (V_acc, g0_acc), None

(V_acc, g0_acc), _ = jax.lax.scan(
    _per_q_body, (V_acc, g0_acc), jnp.arange(n_q_ibz, dtype=jnp.int32))
```

Where `kernel_body` is the existing per-q kernel body (after the WSC split from Issue 1) but inlined for scan composition. With scan, the per-q kernel is compiled once for the scan body and re-executed `n_q_ibz` times by XLA's WhileOp — no Python loop overhead, no per-q `block_until_ready`, and XLA can apply scan-internal optimizations (e.g. donation across iterations).

Important: the outer scan operates on **already-sharded** `zeta_L_all` / `v_q_dev` etc. SPMD has been done. The scan body is the same SPMD-partitioned computation as today's jit, just executed in a loop instead of being called 36 times from Python. The "WhileOp/SPMD trap" from `solve_zeta` doesn't apply because **the carry is the same `V_acc` / `g0_acc` already being passed today**; we're not introducing a new sharded carry. The carry's sharding annotation stays the same as it is in the current per-call donation pattern.

### Issue 3 — WSC density (13 `with_sharding_constraint` calls in the per-q kernel)

Many of the 13 WSCs may be redundant (XLA can infer the sharding from upstream) or counterproductive (forcing transitions XLA could have avoided). After Issues 1+2 are fixed, audit which WSCs are necessary:

- WSCs at jit boundaries (input/output): keep — they pin the contract.
- WSCs on intermediates after a known-safe op: usually redundant.
- WSCs that force a transition XLA wasn't going to make: counterproductive (may trigger their own remats).

Remove the redundant ones, keep the ones at structural boundaries. Target: ≤ 5 WSCs in the per-q kernel.

## Risks

- **Donation pattern with `lax.scan`**: `V_acc` and `g0_acc` are currently donated via `donate_argnums=(0, 1)` on the per-q jit. Under scan, donation works on the scan carry — should be equivalent, but verify the compile actually realizes this and doesn't allocate fresh accumulators per iter.
- **The `q_idx_32 = q_idx.astype(jnp.int32)` pattern inside `fn`**: when q_idx is a Python int (current) vs a traced int32 (under scan), the cast behavior differs. Confirm `dynamic_update_slice` still gets a traced scalar.
- **Bit-identity tolerance**: I'd expect bit-equal (same math, same accumulation order), but if scan-internal accumulation differs, ULP-class drift is acceptable per the same reasoning as Round 5.
